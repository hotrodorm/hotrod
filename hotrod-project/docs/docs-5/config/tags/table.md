# The `<table>` Tag

A `<table>` tag tells the HotRod generator to include a table in the code generation. Each `<table>` tag adds one table
to the persistence layer.


## Attributes

In its simplest form this tag only specifies the table name. All table columns are inspected automatically and all DAO and VO
classes are generated according to the default settings. Names are produced in camel-case and property types are generated
according to the [default types for each database](../supported-databases.md).

The default rules for table and column names can be customized with [`<name-solver>`](./name-solver.md) rules. Data types
can also be customized with [`<type-solver>`](./type-solver.md) rules.

The `<table>` tag can include modifiers that can be useful in special cases, as shown below:

| Attribute | Description | Defaults to |
| --- | --- | --- |
| `name` | The name of the table in natural typing | Required |
| `catalog` | The catalog of the table, if different from the default one | The current catalog, specified in the runtime properties file |
| `schema` | The schema of the table, if different from the default one | The current schema, specified in the runtime properties file |
| `entity` | Sets the base Java name for the Layout, Model, and DAO classes | Camel-case identifier based on the database identifier |
| ~~`java-name`~~ | *Deprecated*. Use `entity` instead |  |
| `implements` | A comma-separated list of fully-qualified classes that will be added to the value object definition using the `implements` java clause | N/A |


## Reserved Words, Non-ASCII Characters, Mixed-Case Identifiers

The configuration allows you to type table, view, and columns names &mdash; their identifiers &mdash; using *natural typing*, as you would do in a typical SQL script. This typing includes:

- Normal ASCII alphanumeric identifiers
- Reserved words
- Identifiers with non-ASCII characters
- Mixed-case identifiers

For the last three cases each database uses different escaping strategies.

In short, special identifiers can be enclosed in single quotes to specify their canonical form. For example, if you created the following table in PostgreSQL with a name that includes a mixed-case letters, a Greek letter, and a space, and that also includes a column whose name is a reserved word:

```sql
CREATE TABLE "Order Type α" ( -- the table name has mixed-case letters, spaces, and a greek letter
  id int primary key,
  "case" VARCHAR(200) -- this column name is a reserved word in PostgreSQL
)
```

You can integrate in HotRod as:

```xml
  <table name="'Order Type α'" entity="OrderTypeA">
    <column name="'case'" property="orderCase" />
  </table>
```

Consider:

1. When dealing with special names, these need to be enclosed in single quotes in the layer configuration file, and using their canonical names
2. The canonical form of an identifier is the name that the database records when an object is created, and using the exact upper case/lower case form
3. There's no need to mention the plain identifiers that don't fall into any of the special categories: `id` in this example
4. To provide useful application names, the attribute `entity` can be used for tables and views. The persistence layer will base the layout and model names in this value
5. To provide useful application names, the attribute `property` can be used for columns. The persistence layer will use this value for the layour members. In this example, the application would find a compilation problem in the persistence layer if the property name was `case` since this is also a reserved word in the application code.

See [Natural Typing Identifiers](../natural-typing-identifiers.md) for more examples.


## Inner Tags

The `<table>` tag can include the following tags:

- Zero or more `<column>` tags to customize table columns.
- An optional `<auto-generated-column>` to configure the auto-generation for the primary key of the table.
- An optional `<version-control-column>` to configure the optimistic locking for this table.
- Zero or more `<sequence>` tags to generate methods that retrieve sequence values.
- Zero or more `<query>` tags to generate methods for parameterized general purpose queries.
- Zero or more `<select>` tags to generate methods for parameterized select queries.


## Customizing Columns

The most common case for customizing columns happens when the name or type generated by the default rules are not convenient for the application. 
In this case the `<column>` tag can directly specify the property name and type for a column. This tag is optional and can be included
only for the columns that need to be superseded.

See the [`<column>`](./column.md) tag for more details.


## Primary Key Generation

Databases implement different stragies when it comes to auto-generated primary keys. Some, use simple auto-increment values, other use both mandatory or optional IDENTITIES (or just one of them) with different syntax rules, while other implement SEQUENCES. Some databases implement them all.

The primary key generation is used when INSERT-ing rows in the database by CRUD and by LiveSQL. CRUD implements single-row INSERTs, while LiveSQL implement single and multi-row INSERTs. All of these clauses will retrieve the newly-generated primary key values to the application automatically.

### Identities

Identities are automatically discovered by the persistence layer. This includes:

- IDENTITY GENERATED ALWAYS
- IDENTITY GENERATED BY DEFAULT
- AUTO_INCREMENT (MySQL, MariaDB)
- SERIAL-like (PostgreSQL)

Since the persistence layer is fully aware of the auto-generation for the primary keys there's no need for any extra configuration.

### Sequences

Sequences, on the other hand, work differently. Since they may or may not be related to a single or multiple tables, the database does not any ability to provide any metadata about their usage.

They need to be configures manually for the primary key column using the `sequence` attribute. For example, we can tell the configuration that the table EMPLOYEE has the column EMPLOYEE_ID that used the sequence SEQ_EMPLOYEE to provide numbers for it when inserting rows using:

```xml
  <table name="employee">
    <column name="employee_id" sequence="seq_employee" />
  </table>
```

See the [&lt;column>](./column.md) tag for details.

### Single-Row INSERTs

CRUD and LiveSQL offer single-row INSERTs. When the application provides a single Layout or Model object to insert, CRUD and/or LiveSQL insert the corresponding row in the database, retrieve the newly generated primary key value, and return this new value to the application in the form of a new object.

### Multi-Row INSERTs

LiveSQL can insert multiple rows using the INSERT/SELECT combination. LiveSQL multi-INSERTs return a list of values that includes one value per inserted row. See [LiveSQL INSERT](../../livesql/syntax/insert.md) for examples.

**Note**: Not all database support multi-primary key retrieval.


### Other Column Generation Rules

Other column generation strategies, such as multi-identities (PostgreSQL), DEFAULT values, GENERATED AS expressions, pre/post INSERT/UPDATE triggers are allowed to work, but the resulting values are not recovered by the persistence layer; an extra SELECT can be executed to retrieve the actual values for the columns that have these special computing rules.


## Optimistic Locking

The default persistence layer does not implement optimistic locking. Tables can be queried and updated freely according to the database rules and isolation levels.

The configuration layer allows you to enable optimistic for a table. When enabled, the update and delete operations are checked to make sure the affected row has not been modified since it was selected.

HotRod ships with three optimistic locking strategies. See [Optimistic Locking](./optimistic-locking.md) for details.

Aside from optimistic locking it's also possible implement Pessimistic Locking using FOR UPDATE or FOR SHARE in SELECT queries. Different database implement different variations of these clauses. Check each engine to find exactly which one of the available options are suitable for your case.


## Custom Persistence Methods

You can configure the table DAO to include extra persistence methods that you may find useful in each specific case.

The configuration allows you to add any number of methods to:

- Retrieve sequences values
- Run non-SELECT queries, with/without parameters, with/without Dynamic SQL
- SELECT queries that return entity rows. That is, rows that match this table definition

See the [`<sequence>`](sequence.md), [`<query>`](query.md), and [`<select>`](select.md) configuration tags.
